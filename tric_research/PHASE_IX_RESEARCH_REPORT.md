# TRIC Phase IX — Native, Control-Calibrated Query-Latency Experiment

**Date:** 21 October 2026. **Status:** Reproducible experimental engineering evidence; **NOT a new-algorithm novelty claim or an O'Reach performance comparison**.

## Research question

Phase VIII optimizes *modeled work* by choosing an ordered certificate-pivot subset. Does the gain remain when the query plane is compiled into C++17 and executes actual BFS fallbacks, and what is the training/amortization cost?

The baseline: a single shared C++17 implementation of graph storage, pivot precomputation, exact certificate checks, and fallback BFS. The only difference between policies is their ordered list of candidate pivots. Policies tested: plain BFS, a duplicate empty-index control, fixed-degree order, coverage greedy, and Phase VIII exact ordered-cost optimization (candidate cap 11, budget 5). Training/selection executes separately in Python, never in the timed query loop.

## Reproduction

```bash
cd tric_research
python -m unittest discover -p 'test_*.py' -q
python benchmark_native.py --test 24000 --repetitions 15 --output phase9_native_results_controlled.json
python benchmark_native.py --trials 1 --test 24000 --repetitions 15 --optimization=-O2 --output phase9_native_results_O2.json
```

Requires Python 3.10+, g++ with C++17. Standard library only. The driver records its compiler version and generated seed configuration. For each graph, the driver draws *disjoint random samples* of training and held-out queries, using the same population of hot endpoints for hot/hot and hot/uniform shift. The C++ executable independently builds the candidate pivot reachability sets and computes every query's exact reachability by BFS **before** query-loop timing. Every returned answer is compared to that independent BFS oracle; a mismatch causes the benchmark to fail.

The C++ runner takes 15 deterministic repetitions with a seeded query shuffle each repetition and a rotating policy execution order. Per-policy median nanoseconds/query is the predeclared summary statistic. Input loading, indexing, oracle construction, warmup, compiler time and Python training are outside timed queries and are reported separately where applicable. Checksums and independent oracle comparisons prevent inadvertently timing skipped work. A byte-matched duplicate of BFS is run as `NoIndexControl`; a ratio outside [0.85,1.15] is a warning against drawing timing conclusions.

## Controlled results: native O3 run

Raw evidence: `phase9_native_results_controlled.json` (24 cases; 8 distinct graphs / 3 workload distributions per graph; each graph n=360; 11 candidate pivots, k=5, train=750, holdout=24,000, 15 repetitions, g++14.2.0 O3 in the tested container).

- Median of per-case **ordered / greedy** compiled query latency ratios: **0.927**. Ordered method faster in **19/24** cases in this run, but the ordering is not always faster.
- Median ordered / BFS latency ratio: **0.486**. Ordered method faster in **19/24** cases.
- Median ordered / fixed-degree ratio: **0.758**.
- **24/24** identical empty-index controls within the 15% sanity bound; median duplicate/control ratio about **0.997**.
- In the held-out *model*, the ordered method beats greedy in 18/24 cases; **three cases have opposing model-versus-native latency preference** (one method is faster in the work model but slower in actual C++), so modeled work is not a wall-clock oracle.
- In the sparse blocks graph family the exact optimizer commonly selects **zero pivots**, matching the principle that an easy BFS fallback is often better than an index. Even then, the near-equal measured nanosecond timings may differ by 1–5%, revealing timing uncertainty rather than real algorithmic work changes.
- Mean Python training+selection time in the O3 trials about **20.6 ms**, mean compiled candidate index building about **0.043 ms**. We report these separately because wall-clock performance alone is not amortized throughput. For cases with positive measured query speed gain over BFS, estimated amortization is `(Python training time + C++ index build time)/(BFS minus indexed nanoseconds/query)`; median finite break-even about **77,000 queries**, with substantial variation and some never-beneficial cases.
- Tests: **46** total Python unit tests, including four compiled C++ tests covering all (s,t) pairs on small DAG/cyclic cases. No correctness failures.

A separate O2 robustness pilot is archived as `phase9_native_results_O2.json` (12 cases, one graph seed per family). Its raw measurements and compiler info must be inspected independently; O2 and O3 runs are not interchangeable.

### Methodology caution

Even these results are **not** strong external evidence: there are only eight distinct graphs, all generated by our code; the 24 cases share graph seeds and are statistically correlated. The CPU container is shared and cannot pin frequency/noise; 10–100 ns/query differences warrant skepticism, especially when the null control reveals fluctuations. Candidate selection is heuristic/high-degree, and both comparators share our exact C++ data plane. Index-build measurements exclude original file parsing and work estimation. Memory has a *logical* bitset footprint estimate but no independently profiled peak process RSS. The model uses edge scans as an imperfect proxy for the cost of BFS. Query distributions are simplistic. Larger paired campaigns and confidence intervals should be performed on dedicated pinned hardware.

## External baseline availability and reproducibility

The *published* O'Reach project has an independent C++ implementation (MIT license) and publishes graph datasets and query files for random, true, false, and mixed reachability. Primary sources:

- Hanauer, Schulz, Trummer, **O'Reach: Even Faster Reachability in Large Graphs**, SEA 2021, https://doi.org/10.4230/LIPIcs.SEA.2021.13
- O'Reach author dataset portal, https://oreach.taa.univie.ac.at/
- O'Reach source, https://github.com/o-reach/O-Reach
- Zhang, Bonifati, Özsu, **Indexing Techniques for Graph Reachability Queries**, ACM Computing Surveys (2025/2026), https://doi.org/10.1145/3776737
- Feige, Lovász, Tetali, **Approximating Min-Sum Set Cover** (2002/2004), https://doi.org/10.1007/s00453-004-1110-5

The O'Reach dataset host could not be resolved by the network-disabled execution container at research time. **No O'Reach binary or real-world graph dataset was downloaded or executed in this phase**. A future publication comparison must use a pinned O'Reach commit, its documented dataset/query formats, identical source graph inputs, independently verified answers, peak RSS, end-to-end preprocessing and query latency under the authors' specified workloads.

## Claims, novelty, and research verdict

| Claim | Evidence | State |
|---|---|---|
| Exact certificates under the supported graph model | Independent BFS comparison in compiled runner; earlier exhaustive Python tests | Supported for tested cases |
| Exact selected permutation minimizes stated deterministic training-work objective | Prior Phase VIII recurrence and exhaustive tests | Mathematically justified, tested |
| Ordered model improves held-out C++ query time in every case | Counterexamples in DAG/SCC cases | **False** |
| Ordered model can beat greedy on some workload structures | 19/24 paired controlled O3 cases | Pilot evidence only |
| Probe-order selection is a novel theoretical primitive | Min-sum set cover literature overlap | **Not established** |
| TRIC beats O'Reach | No head-to-head benchmark | **Not tested** |
| TRIC is submission ready | Novelty/external benchmarks absent | **No-go** |
